# Peer plugins that stay with Obsidian splits and tab stacks

Scope is desktop Obsidian, 2024–2026 sources preferred. Primary plugins: [Vertical Tabs](https://github.com/oxdc/obsidian-vertical-tabs) (oxdc, repo created 2024-07-20, public release notes through 0.18.5) and [Pane Relief](https://github.com/pjeby/pane-relief) (pjeby, still shipping fixes in 2025). The older [Sliding Panes](https://github.com/deathau/sliding-panes-obsidian) plugin (deathau) is included as the layout-owning counterexample those two were written against. Obsidian’s own model, used below: a `WorkspaceSplit` lays children out in a row or column; a `WorkspaceTabs` item (what the 1.0 UI calls a tab group) shows one child leaf at a time. Side docks only contain tab items. See [Workspace](https://docs.obsidian.md/Plugins/User+interface/Workspace).

## How do Vertical Tabs, Pane Relief, and similar plugins open, move, hide, and group tabs?

### Takeaway
Vertical Tabs treats each native tab group (`leaf.parent`, a `WorkspaceTabs`) as the thing it lists, and it opens, moves, and creates groups by calling workspace leaf APIs. Pane Relief does not open or create groups; it reorders leaves inside the current group and navigates among leaves that already exist. Both hide things with CSS classes on the existing tree. Classic Sliding Panes instead writes inline geometry onto root children on every resize.

### Cited Findings
- Vertical Tabs’ feature tour says a tab group “is essentially a workspace split,” so install, uninstall, reload, and restart keep the same layout, and dragging groups “will not affect the overall layout” because groups are ordered topologically. Drag-and-drop in the sidebar is kept in the same order as the horizontal tabs. Per group it offers default (one tab), continuous (tabs as one document), column (side by side), and Mission Control (all tabs previewed). Zen mode hides other groups; an eye icon hides one group; a fold control collapses a group in the sidebar list only. — [Feature tour](https://vertical-tabs-docs.oxdc.dev/User-Guide/feature-tour)
- Opening into a group is a real leaf operation. The file-menu item “Open file in tab group...” calls `workspace.getLeaf("split")`, `leaf.openFile(file)`, then `moveTabToEnd` into that group’s parent. “New group” is only `getLeaf("split")` plus `openFile`. “New group with name...” does the same, then `setGroupTitle(group.id, name)` on `leaf.parent`. — [OpenFile.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/OpenFile.ts)
- `getLeaf("split")` creates a leaf adjacent to the active leaf: direction `"vertical"` puts it to the right, `"horizontal"` puts it below. — [Workspace.getLeaf('split')](https://docs.obsidian.md/Reference/TypeScript+API/Workspace/getLeaf('split'))
- Moving a tab between groups uses the parent’s own methods: `sourceParent.removeChild`, `leaf.setDimension(null)`, `targetParent.insertChild`, `selectTabIndex`, then `workspace.requestResize()`. Moving to the end of a group splices `parent.children`, calls `leaf.setParent`, `selectTab`, `recomputeChildrenDimensions`, detaches the parent if it becomes empty, then calls `workspace.onLayoutChange()` and reapplies ephemeral state on a timeout. — [MoveTab.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/MoveTab.ts)
- “New group” from an existing tab is `duplicateLeaf(source, "split", direction)` then `source.detach()`. Direction is `"horizontal"` when the source group element is taller than it is wide, otherwise `"vertical"`. Multi-select creates the split from the first leaf, detaches the original, then `moveMultipleTabsToEnd` of the rest onto `firstTargetLeaf.parent`. Pinned state and ephemeral state are copied onto the duplicate. — [MoveTab.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/MoveTab.ts)
- Those split calls are wrapped in `runWithCanSplit`, which temporarily makes `Platform.canSplit` return true. The patch is reference-counted and restored in `finally`. A separate `allowCanSplitUniversally` flag exists but the scoped helper does not leave it on. — [PlatformCanSplit.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/PlatformCanSplit.ts)
- Group “view types” are CSS classes on the group element (`vt-default-view`, `vt-continuous-view`, `vt-column-view`, `vt-mission-control-view`), not new workspace item types. `setGroupViewType` calls `group.setStacked(false)` for every type, including default. Continuous, column, and Mission Control then `appendChild` each leaf element onto `group.tabsContainerEl` in `children` order. — [VTGroupView.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/models/VTGroupView.ts), [SortTabDom.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/SortTabDom.ts)
- Continuous view CSS forces every `.workspace-leaf` to `display: block !important`, `contain: unset !important`, `height: unset`, and turns `.workspace-tab-container` into a vertical scrolling column. It hides `.workspace-tab-header-container-inner` and the new-tab / tab-list buttons. Column view is the same with `flex-direction: row` and a min width. Mission Control sets `.workspace-tab-container` to `display: grid`, forces leaf `display: block !important`, hides `.view-header` and the tab-header inner container, and can set `pointer-events: none` on leaf content. — [ContinuousView.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ContinuousView.scss), [ColumnView.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ColumnView.scss), [MissionControlView.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/MissionControlView.scss)
- Hiding a single group adds the class `is-hidden` on that `.workspace-tabs` (the plugin’s own view can be moved to a new group and then `parent.containerEl.addClass("is-hidden")`). Zen mode is a body class `vt-zen-mode` plus the command “Toggle zen mode,” which also calls `lockFocus`. “Show active tabs only” hides inactive `.workspace-tab-header` elements. Auto-hide of the horizontal tab bar toggles `vt-horizontal-tabs-hidden` on the workspace element only when a Vertical Tabs leaf is the active tab of a non-collapsed sidebar (`leftSplit` / `rightSplit` may be null “on layout reload”). — [MoveTab.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/MoveTab.ts), [ZenMode.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/commands/ZenMode.ts), [ShowActiveTabs.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ShowActiveTabs.scss), [HorizontalTabVisibility.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/HorizontalTabVisibility.ts)
- A group’s kind is derived, not stored as a plugin-owned pane: `getGroupType` compares `group.getRoot()` with `leftSplit` and `rightSplit` and otherwise returns root-split. Only root-split groups are offered in “Open file in tab group...”. — [VTWorkspace.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/models/VTWorkspace.ts), [OpenFile.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/OpenFile.ts)
- Pane Relief’s movement commands only reorder `leaf.parentSplit.children` of the active leaf. “Swap tab with previous/next in group” is a relative index. “Place as nth tab in group” is an absolute index, clamped to that same child list. If the parent has `selectTab`, the command splices the array and calls `selectTab`. If it does not, it also moves the DOM node, calls `recomputeChildrenDimensions`, `leaf.onResize`, `workspace.onLayoutChange()`, nulls `activeLeaf`, and `setActiveLeaf`s again. It does not call `getLeaf("split")`. The only new-workspace command found is “Open new window” via `openPopoutLeaf()`. History menu items can `duplicateLeaf` when a modifier is held. — [pane-relief.ts](https://github.com/pjeby/pane-relief/blob/master/src/pane-relief.ts), [Navigator.ts](https://github.com/pjeby/pane-relief/blob/master/src/Navigator.ts)
- Pane Relief navigation walks leaves that already exist (`nav.leaves()`), then `setActiveLeaf`. If the active leaf’s root is the left or right split, it substitutes `getMostRecentLeaf(rootSplit)` (“Workaround for 0.15.3 sidebar tabs stealing focus”). Close-and-go-adjacent activates a neighbor in that same leaf list, then `detach`s. Maximize toggles the class `should-maximize` on the workspace (or hover-editor popover) and refreshes `is-maximized` / `has-maximized` classes; it does not remove leaves. Sliding panes toggles the class `is-sliding` per window and scrolls the active `.workspace-tabs` into view. The class is stored with a `LayoutSetting`, so it survives restart and workspace load. — [pane-relief.ts](https://github.com/pjeby/pane-relief/blob/master/src/pane-relief.ts), [maximizing.ts](https://github.com/pjeby/pane-relief/blob/master/src/maximizing.ts), [sliding.ts](https://github.com/pjeby/pane-relief/blob/master/src/sliding.ts), [README](https://github.com/pjeby/pane-relief/blob/master/README.md)
- Classic Sliding Panes, on resize and after layout ready, reads `rootSplit.children` and assigns inline `flex`, `width`, `left`, and `right`. It replaces `onChildResizeStart` on each root split (“swizzle”). On `layout-change` it only clears inline styles from root children that disappeared; the resize path is what rewrites geometry. Disabling clears those inline styles and restores `onChildResizeStart`. It also `detach`s root leaves whose file was deleted. — [sliding-panes main.ts](https://github.com/deathau/sliding-panes-obsidian/blob/master/src/main.ts)

### Inferences
- “Group” in both maintained plugins is the native `WorkspaceTabs` parent of a leaf. Vertical Tabs will create one, by splitting, when the user asks for a new group. Pane Relief will not; its move commands cannot send a tab into a different group because they never leave `parentSplit.children`.
- Continuous, column, and Mission Control are presentation modes on an existing tab group. They turn off native stacking and then show every leaf at once with CSS. They are not extra splits.
- The safe move path is the one Vertical Tabs uses for ordinary drags: `removeChild` / `insertChild` / `selectTabIndex` / `requestResize`. The risky path is raw `children.splice` plus a manual DOM move plus `onLayoutChange()`, which both plugins still have for some operations.

### Gaps
- Command titles inside Vertical Tabs for “move to new group” were not all enumerated; the file menu strings and the move functions above are what the current master source exposes. A full command-palette dump was not taken from a running Obsidian.
- Hover Editor was not read. Pane Relief only shows that it delegates single-leaf popover maximize to `obsidian-hover-editor` commands and skips `.hover-editor` leaves in one history hook. — [maximizing.ts](https://github.com/pjeby/pane-relief/blob/master/src/maximizing.ts), [Navigator.ts](https://github.com/pjeby/pane-relief/blob/master/src/Navigator.ts)

## Do they create splits themselves, or only reflect the workspace Obsidian already has?

### Takeaway
Vertical Tabs does both: the sidebar reflects `leaf.parent` groups that already exist, and “new group” creates a real split. Pane Relief only reflects and reorders. Classic Sliding Panes does not create splits either, but it restyles the root split’s children as if it owned their geometry.

### Cited Findings
- Author, 6 Nov 2024, on whether tabs from different panes can share a group: “this design is intended to make Vertical Tabs in sync with Obsidian's native UI,” and “in the near future, this is necessary” that groups are arranged in panes. Dragging a vertical tab onto the “new group” button creates a group; dragging a native horizontal tab “anywhere you want” still works. A parallel structure was described as future work, not as the current model: Session, then Group (“split or pane”), then Section. The same thread says the built-in Workspaces plugin “does not work well.” — [Discussion #60](https://github.com/oxdc/obsidian-vertical-tabs/discussions/60)
- The feature tour’s current text (page dated 17 Oct 2026) still defines a tab group as the workspace split Obsidian already persists. It does not describe a Session object. — [Feature tour](https://vertical-tabs-docs.oxdc.dev/User-Guide/feature-tour)
- New groups are created with `getLeaf("split")` or `duplicateLeaf(..., "split", direction)`, which are Obsidian split APIs, not a private pane registry. — [OpenFile.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/OpenFile.ts), [MoveTab.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/MoveTab.ts)
- Phone builds report `Platform.canSplit` false, so Vertical Tabs forces it true only for the duration of those calls. Release 0.17.5 (published 2026-07-05) added “Mobile workspace split support.” Release notes for 0.18.5 say mobile tab groups were re-enabled after Obsidian 1.13.6 had disabled them, “while still keeping Obsidian’s normal behavior.” — [PlatformCanSplit.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/PlatformCanSplit.ts), [0.17.5](https://github.com/oxdc/obsidian-vertical-tabs/releases/tag/0.17.5), [Releases](https://github.com/oxdc/obsidian-vertical-tabs/releases)
- Pane Relief command names switch on `requireApiVersion("0.16")`: the noun is “tab” and the container is “group” on 0.16+, otherwise “pane” and “split.” That is a label over the same `parentSplit.children` reorder. An open feature request on the issue list is “FR: functions that move tabs to other panes/groups” (#52), which matches the code not doing that. — [pane-relief.ts](https://github.com/pjeby/pane-relief/blob/master/src/pane-relief.ts), [Issues](https://github.com/pjeby/pane-relief/issues)
- Sliding Panes’ stylesheet injection sets width on `body.plugin-sliding-panes .mod-root>.workspace-leaf` and `.mod-root>.workspace-split`. It assumes root children are the panes. It does not call `getLeaf("split")`. — [sliding-panes main.ts](https://github.com/deathau/sliding-panes-obsidian/blob/master/src/main.ts)
- After Obsidian 0.16, stacked tabs are a native property of a tab group (`WorkspaceTabs.isStacked`). Pane Relief’s sliding mode reads that flag and widens the group by `--tab-stacked-header-width * --pane-relief-tab-count` instead of inventing a second stack. Its README says this replaces classic Sliding Panes’ stacking and header rotation, which “are now supplied natively by Obsidian 0.16.2.” — [styles.scss](https://github.com/pjeby/pane-relief/blob/master/src/styles.scss), [README](https://github.com/pjeby/pane-relief/blob/master/README.md)

### Inferences
- A sidebar that wants to survive uninstall should store nothing about which leaves exist. Vertical Tabs’ own rationale is that the workspace JSON already is the group list. Names and colors are metadata on `group.id`; the membership is the parent’s `children`.
- Creating a split is appropriate only as the implementation of a user action that Obsidian already calls a split (“new group,” “split”). Doing it from a layout event, or to give the sidebar a private home, is the opposite of the model the author said was required to stay in sync.
- The Nov 2024 “Session / Section” sketch would be a second hierarchy on top of groups. It was not what the Oct 2026 feature tour documents. Shipping it would be the parallel model the same author said was not yet acceptable.

### Gaps
- No source was found that confirms Sessions or in-group Sections shipped. The tour still equates group and workspace split.
- Whether `setGroupTitle` is persisted in workspace data or only in plugin storage was not read (`Customization.ts` was not fetched).

## Do they hide panes with CSS display:none / display:flex on .workspace-split? What issues are reported?

### Takeaway
Yes. Vertical Tabs hides inactive groups by setting `.workspace-split { display: none }` and showing the ones that still contain a visible tab group with `display: flex`. Pane Relief’s maximize mode does the same for splits that do not contain the maximized leaf. Both have filed bugs where the hidden tree also hid toggles, drag regions, empty tab strips, or third-party embeds. Sliding modes that only change `flex` and width have a different bug set: unreachable sidebar tabs and click-through title bars.

### Cited Findings
- With zen mode off, Vertical Tabs’ `ZenMode.scss` does this under `.workspace-split.mod-root`: `.workspace-tabs.is-hidden { display: none }`; every nested `.workspace-split { display: none }`; a split that `:has(.workspace-tabs:not(.is-hidden))` is `display: flex`; a split that `:not(:has(.workspace-tabs))` is also `display: flex`. The comments say the first exception avoids empty containers (#21) and the second keeps “Excalidraw embeds, custom plugin containers” visible (#166). — [ZenMode.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ZenMode.scss)
- With `body.vt-zen-mode`, inactive `.workspace-tabs` (not `.mod-active` and not `.vt-mod-active`) get `display: none` and `flex-basis: unset`. The active tab group gets `display: flex` and `flex-basis: 100%`. Ancestor `.workspace-split`s that contain the active group get `flex-basis: 100%`. The body also sets `--tab-stacked-pane-width: 100%`. Zen mode docs say inactive groups are hidden and the active split uses the full width. — [ZenMode.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ZenMode.scss), [Zen mode](https://vertical-tabs-docs.oxdc.dev/Features/zen-mode)
- Reported consequence, 5–6 Nov 2024 (Obsidian desktop, Vertical Tabs): “Split pane” appeared only as another copy in the sidebar. Maintainer: zen mode was hiding the inactive splits. Disabling it showed the other panes. — [Issue #57](https://github.com/oxdc/obsidian-vertical-tabs/issues/57), [Discussion #60](https://github.com/oxdc/obsidian-vertical-tabs/discussions/60)
- Auto-hide of horizontal tabs does not set `display` on `.workspace-split`. It sets `.workspace-tab-header-container { display: none }` under `.workspace.vt-horizontal-tabs-hidden > .workspace-split.mod-root`, then `display: flex` on replacement header buttons, and restores left/right sidebar toggles with CSS variables. On a frameless window it sets `-webkit-app-region: drag` on the view header and `no-drag` on icons. The stylesheet comment ties this to issues #176, #206, and #247. — [AutoHideHorizontalTabs.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/AutoHideHorizontalTabs.scss)
- Issue #206 asks that auto-hide apply only while the Vertical Tabs sidebar tab is the visible one. The reporter’s complaint was that hiding the horizontal headers whenever the sidebar is open leaves no tab UI while File Explorer or Outline is selected. Their stopgap CSS uses `.workspace:has(> .workspace-split.mod-sidedock ... .workspace-tab-header.is-active.obsidian-vertical-tabs-tab-header)` and `display: none` on the root `.workspace-tab-header-container`. Current `refreshSelfVisibilityLabels` matches that narrower condition: the class is set only when the Vertical Tabs leaf is the selected tab of a non-collapsed, non-null sidebar. — [Issue #206](https://github.com/oxdc/obsidian-vertical-tabs/issues/206), [HorizontalTabVisibility.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/HorizontalTabVisibility.ts)
- “Show active tabs only” sets `display: none` on `.workspace-tab-header:not(.is-active)` inside `.workspace-split.mod-root`, and on the active header sets `container-type: unset` with a comment “fix tab width from Obsidian 1.8.0.” — [ShowActiveTabs.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ShowActiveTabs.scss)
- Background mode, 7 Jan 2025, Obsidian 1.8.0, macOS, Vertical Tabs 0.13.0: after restart, the left sidebar showed an empty tab strip. The reporter identified `.workspace .mod-sidedock.mod-left-split`’s last `.workspace-tabs`. It did not reproduce until restart. Closed 12 Jan 2025 with “A fix will be available soon.” — [Issue #101](https://github.com/oxdc/obsidian-vertical-tabs/issues/101)
- Pane Relief maximize CSS, under `.workspace.should-maximize .workspace-split.mod-root` (and the same for a hover popover): `display: none` on `.workspace-leaf:not(.is-maximized)`, `.workspace-tabs:not(.has-maximized)`, the maximized group’s tab header container, and `.workspace-split:not(.has-maximized)`. The maximized leaf’s `.view-header` is `display: flex`. A cloned right-sidebar toggle `#pr-maximize-sb-toggle` is `display: none` until `.workspace.should-maximize` is present, because the real toggle is covered. — [styles.scss](https://github.com/pjeby/pane-relief/blob/master/src/styles.scss), [maximizing.ts](https://github.com/pjeby/pane-relief/blob/master/src/maximizing.ts)
- Maximize bugs that followed that hiding: 0.5.0 notes say toggling maximize while a sidebar leaf was active used to hide the main area; it now maximizes the most recent main-area leaf. The same release says dragging and clicking at the top of a non-native frame were broken, and the styling was rewritten for Obsidian, hidden, and native frames, “only been tested on Windows.” 0.5.7/0.5.8 notes restore a view-header icon Obsidian 1.6 removed, so a maximized view can still be dragged; the code creates that icon in `ItemView.load` and points `dragstart` at `workspace.onDragLeaf`. Release 0.5.9 (22 Feb 2025) “Fix unreachable right sidebar tabs w/maximized and/or sliding panes.” Issue #56 on the issue list is “Pinned state not visible when maximized.” — [Releases](https://github.com/pjeby/pane-relief/releases), [0.5.9](https://github.com/pjeby/pane-relief/releases/tag/0.5.9), [maximizing.ts](https://github.com/pjeby/pane-relief/blob/master/src/maximizing.ts), [Issues](https://github.com/pjeby/pane-relief/issues)
- Sliding panes in Pane Relief does not use `display: none` on splits. `.mod-root.is-sliding` sets `overflow-x: auto`, `flex: none`, and a fixed width (`--pr-sliding-panes-width`, default 700px) on root children, and `display: block` on `.workspace-leaf`. Stacked groups add header width times tab count. The right toggle is `position: fixed`. An overlay div exists because scrolled panes’ headers steal `-webkit-app-region` from the title bar. — [styles.scss](https://github.com/pjeby/pane-relief/blob/master/src/styles.scss), [sliding.ts](https://github.com/pjeby/pane-relief/blob/master/src/sliding.ts)
- Issue #47 (25 Apr 2023, Obsidian 1.1.16): with sliding panes on, the right sidebar toggle moved to the far right and was not clickable. Maintainer’s first workaround set `-webkit-app-region: no-drag` and “makes it impossible to drag the window.” Fixed in 0.4.2 the same day. README still calls sliding panes beta: “scrolling may be jumpy or require manual adjustment if a given stacked tab set does not fit the application window.” — [Issue #47](https://github.com/pjeby/pane-relief/issues/47), [README](https://github.com/pjeby/pane-relief/blob/master/README.md)
- Classic Sliding Panes is the plugin Pane Relief says must be disabled and followed by an Obsidian restart, because “the Sliding Panes plugin does not properly uninstall all of its hooks when disabled” and those hooks interfere with stacked tabs and with Pane Relief’s sliding mode. — [README](https://github.com/pjeby/pane-relief/blob/master/README.md), [0.3.0 notes](https://github.com/pjeby/pane-relief/releases/tag/0.3.0)
- Forum, “Cannot resize tabs”: after installing and uninstalling the old sliding-panes plugin, a user could not drag pane widths and could not place two tabs side by side. A reply said native stacked tabs have no pointer resize; width is `--tab-stacked-pane-width` (default 700px). The thread does not show a maintainer confirming leftover hooks in that vault. — [Cannot resize tabs](https://forum.obsidian.md/t/cannot-resize-tabs/66097)
- Forum, 6 Mar 2026: `animation: none` on `.workspace-leaf-content` leaves both sidebars blank after reload. A reply says sidebar leaf content is drawn by a “node inserted” animation on `.node-insert-event`; disabling that animation skips the draw. `animation: unset` did not trigger it. — [Sidebar content disappears](https://forum.obsidian.md/t/bug-sidebar-content-disappears-after-reload-when-custom-css-disables-animation/111977)
- A 9 Oct 2025 Reddit thread says sliding panes and even `Cmd-T` stopped after an update, and one reply says tabs looked invisible until community plugins were turned off. Another reply says the Sliding Panes plugin’s last update was years ago and it is gone from the community directory. This is anecdote, not a reproduction. — [r/ObsidianMD](https://www.reddit.com/r/ObsidianMD/comments/1o2gn48/sliding_panes_and_even_tabs_not_working/)

### Inferences
- `display: none` on `.workspace-split` removes the split from flex layout, so Obsidian’s resize math and drag targets no longer match what the user sees. Both maintained plugins then put `display: flex` back on the one branch that should remain. The bugs are the branches they forgot: splits with no `.workspace-tabs` (embeds), the right sidebar toggle, the window drag region, and the main area when the active leaf is a sidebar leaf.
- Hiding `.workspace-tab-header-container` is safer than hiding the split, but it removes the only place Obsidian paints sidebar toggles and the frameless drag strip. Both plugins had to paint those back.
- A class such as `is-hidden` that is not part of the workspace layout will not round-trip through a restart. Issue #101 is the sidebar form of that: an empty `.workspace-tabs` appears after reload because the hide did not stick, or a leaf was created and then only hidden in the DOM.
- Changing `flex` / `width` on root children without `display: none` still breaks drag and stacked-tab width, which is the Sliding Panes failure mode. It is not a gentler version of the same trick.

### Gaps
- Issue bodies for Vertical Tabs #21, #166, #176, and #247 were not fetched. The #21 and #166 behavior is taken from comments in `ZenMode.scss`, not from the issue text.
- No 2024–2026 forum thread was found whose title is specifically “plugin breaks pane drag after an update” with a maintainer diagnosis. The closest dated reports are Vertical Tabs #57 (Nov 2024), #101 (Jan 2025), Pane Relief 0.5.0/0.5.9 notes, and the March 2026 animation bug.

## What action vocabulary do they show the user, versus a parallel group that owns a pane?

### Takeaway
They use Obsidian’s words: tab, group, split, and stack. A “group” is the tab stack that already owns the leaves. Neither shipped plugin shows a group that owns a pane from outside the workspace tree. Vertical Tabs adds view modes (continuous, column, mission control, zen) as commands on the current group. Pane Relief’s verbs are jump, place, swap, cycle, maximize, and toggle sliding panes.

### Cited Findings
- Vertical Tabs commands registered in source: “Set current group as default view,” “Set current group as continuous view,” “Set current group as column view,” “Set current group as mission control view,” and “Toggle zen mode.” File menu: “Open file in tab group...”, then each group’s title, “New group,” and “New group with name...”. Docs also say drag onto a “new group” button, and that native split still works. — [GroupView.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/commands/GroupView.ts), [ZenMode.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/commands/ZenMode.ts), [OpenFile.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/OpenFile.ts), [Discussion #60](https://github.com/oxdc/obsidian-vertical-tabs/discussions/60)
- The author told a user who wanted one group to contain tabs from different panes that this is not how it works, and pointed them at drag-and-drop into an existing group (which moves the leaf into that group’s parent). — [Discussion #60](https://github.com/oxdc/obsidian-vertical-tabs/discussions/60)
- Setting a non-default view calls `group.setStacked(false)`. Stacking stays Obsidian’s feature. Zen mode only overrides `--tab-stacked-pane-width`. — [VTGroupView.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/models/VTGroupView.ts), [ZenMode.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ZenMode.scss)
- Pane Relief command strings, with 0.16+ nouns: “Swap tab with previous in group,” “Swap tab with next in group,” “Cycle to previous tab in this window,” “Cycle to next tab in this window,” “Jump to 1st tab in window” through “Jump to last tab in window,” “Place as 1st tab in group” through “Place as last tab in group,” “Maximize active tab (Toggle),” “Close tab and go to adjacent tab,” “Open new window,” plus “Toggle sliding panes (for current window)” in `sliding.ts`. Cycle/jump ignore group boundaries and walk the window’s leaf list; place/swap stay inside the current group. — [pane-relief.ts](https://github.com/pjeby/pane-relief/blob/master/src/pane-relief.ts), [sliding.ts](https://github.com/pjeby/pane-relief/blob/master/src/sliding.ts)
- README describes those place/swap commands as the way to reorder tabs “when stacking or sliding them,” and says Alt+1–8 can reserve positions for documents that stay open. It does not offer “move to group.” — [README](https://github.com/pjeby/pane-relief/blob/master/README.md)
- Open requests that would extend the vocabulary, not current commands: #52 “functions that move tabs to other panes/groups,” #57 “keyboard shortcut to focus on first, second, ... tab group,” #64 “Close tab and go to adjacent tab: causes focus to be on right tab group” (opened 19 Feb 2025). The #64 title is from the issue index; the thread body was not read. — [Issues](https://github.com/pjeby/pane-relief/issues)
- Obsidian’s developer docs use “split” and “tabs,” not a third container. Side-dock splits only contain tab items. — [Workspace](https://docs.obsidian.md/Plugins/User+interface/Workspace)

### Inferences
- User-facing “group” should mean `leaf.parent` in the root split. “New group” should mean split. “Move to group” should mean `removeChild` / `insertChild` into that parent. “Stack” should mean `setStacked`, which Vertical Tabs explicitly turns off before its own multi-leaf views.
- A sidebar heading that is not one of those parents will drift from the layout as soon as the user drags a native tab, reloads, or disables the plugin. That is the failure the Vertical Tabs author refused in November 2024.
- Pane Relief’s “place as nth tab in group” is easy to misread as a window-wide slot. The implementation is the index inside the current tab stack only. A sidebar should not copy that name if it means “nth editor group.”

### Gaps
- Vertical Tabs’ full context-menu phrase list (beyond the file menu and the group-view commands) was not extracted from `Menu.ts`.
- No second maintained sidebar plugin from 2024–2026 was found that both lists open editor tabs and refuses to create splits. Vertical Tabs is the one that lists them; Pane Relief is the one that only reflects them.

## What should a sidebar plugin never do during layout-change or on vault load?

### Takeaway
During `layout-change` and while the workspace is loading, a sidebar should rebuild its list from the tree Obsidian just finished. It should not create, detach, or restyle splits, and it should not register its view or patch `Platform.canSplit` in that window. The bugs above are what happens when a plugin writes the tree or hides it in the same turn Obsidian is measuring it.

### Cited Findings
- `layout-change` fires for many unrelated reasons, including mode changes, and can run before the DOM the handler wants exists. A 2023 forum note used `setTimeout` because embedded markdown was not in the DOM yet. Calling `workspace.onLayoutChange()` from a move (Vertical Tabs’ `moveTabToEnd` and `moveMultipleTabsToEnd` do this) re-enters every `layout-change` listener, including other plugins. — [mode-change thread](https://forum.obsidian.md/t/add-an-obsidian-event-for-whenever-a-leaf-changes-from-source-mode-to-preview-mode/64117), [MoveTab.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/MoveTab.ts)
- Registering a custom view inside `onLayoutReady` replaces existing views of that type with `EmptyView`. Forum, 16 Mar 2026: `getLeavesOfType` inside `onLayoutReady` returned `[]` for a leaf that was open before quit; the fix given was to call `registerView` in `onload`, before layout ready. — [Custom views not detected](https://forum.obsidian.md/t/bug-custom-views-are-not-detected-while-opening-obsidian-in-onlayoutready-callback/112337)
- Vertical Tabs’ own visibility helper says `leftSplit` / `rightSplit` “can be null on layout reload,” and returns false instead of touching them. — [HorizontalTabVisibility.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/HorizontalTabVisibility.ts)
- Pane Relief installs history before other features and waits for `onLayoutReady` to subscribe to rename and active-leaf events. Its README says that if a startup hack delays plugins, Pane Relief must load before the workspace or it cannot load history, focus lock, or sliding-panes settings, and that disabling it before exit or before a workspace load drops that saved state. — [pane-relief.ts](https://github.com/pjeby/pane-relief/blob/master/src/pane-relief.ts), [README](https://github.com/pjeby/pane-relief/blob/master/README.md)
- Sliding Panes calls `workspace.getLeaf()` with no arguments inside `recalculateLeaves`, which runs from `resize` and from `reallyEnable` after layout ready, and uses the result as the leaf to scroll to. The same plugin replaces `onChildResizeStart`. Pane Relief’s README says those hooks are still installed after the plugin is disabled and break stacked tabs until restart. The copy of `disable()` read here does call `unswizzleChildResize` and `workspace.off`; the reported failure is that this cleanup does not always run. — [sliding-panes main.ts](https://github.com/deathau/sliding-panes-obsidian/blob/master/src/main.ts), [README](https://github.com/pjeby/pane-relief/blob/master/README.md)
- Hiding every `.workspace-split` and then forcing one to `display: flex` is exactly the zen-mode and maximize stylesheets. Users then report splits that “did nothing” (Nov 2024), a main pane that disappears when a sidebar leaf is active (Pane Relief 0.5.0), and right-sidebar tabs that cannot be reached (0.5.9, Feb 2025). The stylesheet authors had to special-case splits that contain no `.workspace-tabs`. — [ZenMode.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ZenMode.scss), [styles.scss](https://github.com/pjeby/pane-relief/blob/master/src/styles.scss), [Issue #57](https://github.com/oxdc/obsidian-vertical-tabs/issues/57), [Releases](https://github.com/pjeby/pane-relief/releases)
- Forcing every leaf in a tab group to `display: block !important` and `contain: unset` (continuous, column, mission control) shows leaves Obsidian’s tab group is supposed to hide. The plugin’s mitigation is `setStacked(false)` plus re-appending leaf DOM in `children` order after every such move. Doing the CSS without those two steps leaves the visual order and the workspace array different, which is the drag/stack break. — [ContinuousView.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ContinuousView.scss), [VTGroupView.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/models/VTGroupView.ts), [SortTabDom.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/SortTabDom.ts)
- `animation: none` on `.workspace-leaf-content` blanks sidebar leaves after reload, because Obsidian inserts them with `.node-insert-event`. — [Sidebar content disappears](https://forum.obsidian.md/t/bug-sidebar-content-disappears-after-reload-when-custom-css-disables-animation/111977)
- A later Pane Relief fix “allow[s] sidebar tabs to be programmatically revealed, even if focus lock is enabled,” so hotkeys and file reveal still work. The earlier behavior blocked that reveal. `gotoNthLeaf` also refuses to treat a sidebar leaf as the thing to cycle. — [Releases](https://github.com/pjeby/pane-relief/releases), [pane-relief.ts](https://github.com/pjeby/pane-relief/blob/master/src/pane-relief.ts)

### Inferences
A sidebar plugin should not do any of the following during `layout-change`, `resize`, or vault/workspace load:

- Create a leaf or a split (`getLeaf("split")`, `duplicateLeaf`, no-argument `getLeaf()`), or `detach` one, to “repair” the sidebar’s home. Build the list from `iterateAllLeaves` / each leaf’s `parent`. Create a split only from an explicit user command.
- `registerView` in `onLayoutReady`. Do it in `onload` before the layout is applied, or a restored leaf of that type becomes an empty view and the sidebar cannot find itself.
- Touch `leftSplit` or `rightSplit` without a null check. On layout reload they can be null.
- Patch `Platform.canSplit`, `onChildResizeStart`, or `ItemView.load` from a layout event, or leave the patch installed after `onunload`. Cleanup that only runs from a settings “disable” path is how Sliding Panes outlived itself.
- Write `display`, `flex`, `width`, `left`, or `right` onto `.workspace-split` or root children from a layout handler. If a user command hides groups, scope `display: none` to `.workspace-tabs.is-hidden`, keep `display: flex` on splits that have no `.workspace-tabs`, and do not apply it while the active leaf is in a side dock.
- Hide `.workspace-tab-header-container` without restoring the side-dock toggles and the frameless `-webkit-app-region` drag/no-drag split. Both plugins’ bug trackers are this mistake.
- Set `display: block !important` on `.workspace-leaf` inside a tab group unless native stacking is off and the DOM order is rewritten to match `parent.children` in the same turn.
- Call `workspace.onLayoutChange()` from inside a `layout-change` handler. Refresh the sidebar from the event; let Obsidian be the one to emit it.
- Persist “this group is hidden” only as a DOM class. After restart the empty tab strip comes back (Vertical Tabs #101).
- Steal `setActiveLeaf` for sidebar leaves so thoroughly that a hotkey cannot reveal them. If the sidebar is not the active tab, leave the main leaf focused (Pane Relief’s `getMostRecentLeaf(rootSplit)` workaround).
- Assume the workspace JSON has been applied if the plugin itself was delayed past layout load. Read layout after `layoutReady`; do not mutate it to compensate.

### Gaps
- The exact `onunload` path of current Sliding Panes (`plugin-base`) was not read, so the claim that hooks survive disable is pjeby’s report, not a line-by-line confirmation of today’s `onunload`.
- No source stated a single official “never do this in layout-change” rule. The list above is the intersection of the bugs and the guards already present in Vertical Tabs and Pane Relief.
