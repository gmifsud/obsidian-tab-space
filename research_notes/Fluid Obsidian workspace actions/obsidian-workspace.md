## What do mod-vertical and mod-horizontal mean on .workspace-split, and how are child sizes set (flex, height 0, width 0)?

### Takeaway
`mod-vertical` means children sit in a row (side by side). `mod-horizontal` means children sit in a column (one under another). Both size their direct children with `flex: 1 0 0` plus a zero length on the main axis (`width: 0` for vertical, `height: 0` for horizontal) so content cannot force the pane open. The stored size is a percentage written to inline `flexGrow`.

### Cited Findings
- A split is created with class `workspace-split` and immediately calls `setDirection`. That method is `setDirection(e){this.containerEl.removeClass("mod-"+this.direction),this.direction=e,this.containerEl.addClass("mod-"+e)}`. Direction `"vertical"` therefore becomes class `mod-vertical`, and `"horizontal"` becomes `mod-horizontal`. The string `mod-horizontal` does not occur as a literal; it is concatenated. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- CSS for the two directions, quoted from `app.css`:

```css
.workspace-split{display:flex;background-color:var(--tab-container-background);position:relative}
.workspace-split.mod-vertical{flex-direction:row}
.workspace-split.mod-horizontal{flex-direction:column}
.workspace-split.mod-vertical>*{height:100%;flex:1 0 0;width:0}
.workspace-split.mod-horizontal>*{width:100%;flex:1 0 0;height:0}
```

— [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)

- `flex: 1 0 0` is grow 1, shrink 0, basis 0. The zero `width` or `height` is the main-axis length. The other axis is `100%`. These rules apply only to direct children (`>*`), which are nested splits or tab groups, not the leaves inside a tab group. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Persisted size is not a pixel width. `setDimension` clamps a value `<= 0` or `>= 100` to `null`, stores `this.dimension`, and sets `containerEl.style.flexGrow` to that number or to `""` when null: `setDimension(e){e!==null&&(e<=0||e>=100)&&(e=null),this.dimension=e;let{containerEl:i}=this,r="";e&&(r=String(e)),i.style.flexGrow=r}`. `flexGrow` overrides only the grow factor of `flex: 1 0 0`. Shrink stays 0 and basis stays 0. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `recomputeChildrenDimensions` sums child `dimension` values and rewrites each as `100 * dimension / sum`. If any child has `dimension == null`, every child is set to `null` (equal `flex: 1 0 0`). — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- While the user drags a divider, sizes become pixels. `getElSize` returns `offsetWidth` when `direction === "vertical"` and `offsetHeight` when `direction === "horizontal"`. `setElSize` sets `flex: 0 0 auto` and then either `width` (vertical) or `height` (horizontal) in pixels. `finishResize` calls `unsetElSize`, which clears inline `flex`, `width`, and `height`, then writes the pixel ratio back through `setDimension` as a percentage. The drag refuses to shrink a child below `R0e`, which is `200` (`var R0e=200`). — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Divider geometry follows the same classes. Horizontal splits put `.workspace-leaf-resize-handle` on the bottom, full width, `cursor: row-resize`. Vertical splits, and the primary and secondary docks, put it on the inline end, `cursor: col-resize`. The root split's own handle is `display: none`. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Side docks are splits too, but they do not share that flex. They add `mod-sidedock` plus both `mod-primary-split` or `mod-secondary-split` and `mod-left-split` or `mod-right-split` (`vc` maps `left` to `primary` and `right` to `secondary`). CSS is `.workspace-split.mod-primary-split,.workspace-split.mod-secondary-split{flex:0 0 auto}`. Width is an inline pixel value from `setSize` (`this.containerEl.style.width = \`${e}px\``), default `this.size = 300`, not `flexGrow`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar); [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- The desktop workspace element’s children are left ribbon, left dock, root split, right dock, right ribbon. `.workspace>.workspace-leaf,.workspace>.workspace-split{height:100%;width:100%}`. The docks then override width with the pixel size above. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar); [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Every leaf is `.workspace-leaf{display:flex;flex-direction:column;position:relative;contain:strict!important;overflow:hidden;isolation:isolate}`. Tab groups are `.workspace-tabs{overflow:hidden;display:flex;flex-direction:column;position:relative}` and `.workspace-tabs>*{flex:1 0 0}`. The header later sets `flex: 0 0 auto` and `height: var(--header-height)` at equal specificity, so the header stays a fixed strip and the `.workspace-tab-container` keeps `flex: 1 0 0`. Leaves inside a tab group are `.workspace-tab-container>*{flex:1 0 0}` and `.workspace-tabs .workspace-leaf{height:100%}`. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)

### Inferences
- `mod-vertical` names the divider (a vertical line between columns). The CSS main axis for that class is a row. `mod-horizontal` names a horizontal divider between rows, and the CSS main axis is a column.
- A plugin that writes pixel `width` or `height` on a split’s direct children is using the temporary resize channel. After `finishResize` those inline sizes are cleared and only `flexGrow` remains. Re-applying pixel sizes on every `layout-change` pins the panes and discards the percentage model.
- `width: 0` and `height: 0` are safe only because `contain: strict` on the leaf stops content min-size from expanding the flex item, and because `flex-basis` is 0. Those two rules are one mechanism.

### Gaps
- The rendered method pages for `getLeaf` and `createLeafBySplit` on docs.obsidian.md returned an empty body when fetched, so the public wording is taken from the indexed Workspace reference rather than a full page capture.

## How do stacked tabs work (mod-stacked, setStacked, stack tabs menu/command)? How is that different from a horizontal split?

### Takeaway
Stacked tabs are a mode of one tab group, not a split direction. `setStacked(true)` adds `mod-stacked`, shows every leaf at once, and moves each tab header into the scrolling row beside its leaf. A horizontal split is a different parent: several tab groups in a column, each normally showing one leaf, with a resize handle between them.

### Cited Findings
- Official workspace model: a split lays children out one after another on a vertical or horizontal direction. A tabs item displays one child at a time and hides the others. Root, left, and right are splits. Side docks are documented as split, then tabs, then leaves. — [Workspace](https://docs.obsidian.md/Plugins/User+interface/Workspace)
- `setStacked` is on the tab group: `setStacked(e){S.canStackTabs||(e=!1),this.isStacked!==e&&(this.isStacked=e,this.containerEl.toggleClass("mod-stacked",e),this.children.length>0&&(this.updateTabDisplay(),this.scrollIntoView(this.currentTab),this.workspace.requestUpdateLayout()))}`. `canStackTabs` is `!S.isPhone`. Serialization writes `stacked: true` only when `isStacked` is set. Deserialize calls `setStacked(true)` when `e.stacked` is set, then `selectTabIndex`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- The command is registered only when `canStackTabs` is true: id `workspace:toggle-stacked-tabs`, name from `w.commands.toggleStackedTabs()`, icon `lucide-layers`. The callback requires `activeLeaf.parent` to be a tab group, then returns without toggling when that group’s root is `leftSplit` or `rightSplit`. Otherwise it calls `setStacked(!isStacked)`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- The tab-list menu (chevron on the tab header) adds the same toggle only when `getRoot() instanceof Ro` is false, titled `stackTabs()` or `unstackTabs()` from `w.interface.menu`, icon `lucide-layers`, click `setStacked(!this.isStacked)`. Sidebar tab groups do not get the menu item. The workspace also fires `tab-group-menu` with the menu and this tab group before the per-tab items. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `updateTabDisplay` when stacked pushes each header and then each leaf into the tab container (`setChildrenInPlace` of that interleaved list), calls `containerEl.toggle(true)` for every leaf, and loads deferred leaves. When not stacked, only the current leaf is toggled visible and headers stay in the header strip. `selectTabIndex` removes `is-hidden` from the current leaf when stacked. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `updateSlidingTabs` returns immediately when not stacked and clears inline `left`, `right`, `minWidth`, and `maxWidth` on headers and leaves. When stacked, it sums header `offsetWidth`, sets each header’s `left` and `right`, and sets each leaf’s `left`, `minWidth` (`max(300, containerWidth - headerSum) / count`), and `maxWidth` (`max(300, containerWidth - headerSum)`). A `ResizeObserver` on the tab container calls this. `onContainerScroll` adds `is-hidden` to stacked leaves whose box is fully outside the scrollport. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Stacked CSS is scoped to `.workspace .mod-root .workspace-tabs.mod-stacked`. Quoted rules:

```css
.workspace .mod-root .workspace-tabs.mod-stacked .workspace-tab-container{overflow-x:auto;overflow-y:hidden;position:relative;display:flex;flex-direction:row}
.workspace .mod-root .workspace-tabs.mod-stacked .workspace-tab-container>*{flex:0 0 auto;position:sticky}
.workspace .mod-root .workspace-tabs.mod-stacked .workspace-tab-container .workspace-tab-header{width:var(--tab-stacked-header-width);writing-mode:var(--tab-stacked-text-writing-mode);text-orientation:sideways;background-color:var(--background-primary);padding:0;border-radius:0;box-shadow:-1px 0 0 0 var(--tab-outline-color),var(--tab-stacked-shadow);--no-tooltip: true}
.workspace .mod-root .workspace-tabs.mod-stacked .workspace-tab-container .workspace-leaf{width:var(--tab-stacked-pane-width);contain:strict}
.workspace .mod-root .workspace-tabs.mod-stacked .workspace-tab-container .workspace-leaf.is-hidden>*{display:none}
```

Defaults on `body`: `--tab-stacked-pane-width: 700px`, `--tab-stacked-header-width: var(--header-height)`, `--tab-stacked-text-writing-mode: vertical-lr`, `--tab-stacked-text-transform: rotate(0deg)`. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)

- The non-stacked child rule `.workspace-tab-container>*{flex:1 0 0}` is what a single visible leaf uses to fill the row. The stacked rule replaces that with `flex: 0 0 auto` and `position: sticky`, so each pane keeps its own width and can overlap as the row scrolls. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- A horizontal split is the other object. `mod-horizontal` sets `flex-direction: column` on a `workspace-split`, and each direct child is usually its own tab group with `height: 0` and a bottom resize handle. Those children do not get `mod-stacked` from the split. Each of those tab groups still shows one leaf unless that group’s own `isStacked` is true. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar); [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Closing the last leaf in a tab group stores `workspace.lastTabGroupStacked = this.isStacked`. If `updateLayout` later finds `rootSplit.children.length === 0`, the replacement tab group is created with `setStacked(true)` when that flag is set. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `WorkspaceTabs.setStacked(stacked: boolean)` is documented as an unofficial API: “Enables or disables stacked tab display.” — [setStacked typings](https://obsidian-typings.github.io/obsidian-typings/public/api/obsidian/augmentations/WorkspaceTabs/setStacked/)
- Linked leaf groups (`leaf.group` / `setGroup`) are a third object. `updateLayout` clears a group id when only one leaf still carries it. That is not a tab group and not `mod-stacked`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)

### Inferences
- A plugin that wants sliding panes should call `setStacked` on the leaf’s parent tab group and leave the surrounding split direction alone. Creating a horizontal split produces separate resizable panes, each with its own tab header strip.
- The stacked stylesheet does not match sidebar tab groups, because every stacked rule requires `.mod-root`. The menu and command already refuse sidebars. Calling `setStacked(true)` on a sidebar group anyway would still flip the class, show every leaf, and interleave headers, without the root stacked width and sticky rules.
- `is-hidden` hides the leaf’s children, not the leaf box. The leaf stays in the flex row so scroll width and sticky headers still work.

### Gaps
- The English menu strings are not literals in `app.js` or in `i18n/en-GB.txt` (that file is 7615 bytes of newlines). The stable names are the command id `workspace:toggle-stacked-tabs` and the functions `stackTabs`, `unstackTabs`, and `toggleStackedTabs`.
- The help page `https://help.obsidian.md/User+interface/Workspace/Stacked+tabs` returned an empty body when fetched.

## How does createLeafBySplit(direction) map to those classes? What does direction 'vertical' vs 'horizontal' mean in the API versus the UI words "split right" and "split down"?

### Takeaway
API `"vertical"` is the UI split to the right: class `mod-vertical`, panes in a row. API `"horizontal"` is the UI split down: class `mod-horizontal`, panes in a column. `createLeafBySplit` builds a new leaf, wraps it in a new tab group, and inserts that group beside the source, nesting a new split only when the requested direction differs from the parent split.

### Cited Findings
- Public `getLeaf` text: “If direction is `'vertical'`, the leaf will appear to the right. If direction is `'horizontal'`, the leaf will appear below the current leaf.” `getLeaf('split', direction)` is the split form of that method. — [Workspace reference](https://docs.obsidian.md/Reference/TypeScript+API/Workspace)
- The same sentence is in the community typings for `getLeaf('split', direction?)`. `createLeafBySplit(leaf, direction?: SplitDirection, before?: boolean)` is marked official since 0.9.7. `SplitDirection` is the direction argument of `splitActiveLeaf`, `splitLeaf`, and `createLeafBySplit`. — [obsidian-typings Workspace.d.ts](https://github.com/Fevol/obsidian-typings/blob/3.16.6/src/obsidian/augmentations/Workspace.d.ts); [createLeafBySplit](https://obsidian-typings.github.io/obsidian-typings/public/api/obsidian/augmentations/Workspace/createLeafBySplit/)
- Installed `app.js` matches those signatures. `getLeaf(e,i){return e==="split"?this.splitActiveLeaf(i):e==="tab"||e===!0?this.createLeafInTabGroup():e==="window"?this.openPopoutLeaf():this.getUnpinnedLeaf()}`. `createLeafBySplit(e,i,r)` on phone (`!canSplit`) creates a leaf in the source parent tab group instead of splitting. Otherwise it does `splitLeaf(e, new leaf, i, r)` and activates the new leaf. `splitActiveLeaf` uses the most recent leaf, then `createLeafBySplit`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `splitLeaf(e,i,r="vertical",n)` walks from the source leaf up to the nearest `Jn` split. If the inserted item is not already a tab group, it wraps it with `rt.createFrom`. If `r !== parent.direction`, it sets the source dimension to `null`, creates `new Jn(this, r)` (which calls `setDirection` and therefore adds `mod-vertical` or `mod-horizontal`), replaces the source in the old parent with that new split, and puts the new tab group and the source inside it. `n` true inserts the new item first (`before`). If the direction matches the parent, it halves a non-null dimension and inserts a sibling in that same split. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Omitted direction uses the default parameter `"vertical"`. So `createLeafBySplit(leaf)` and `getLeaf("split")` with no direction add a `mod-vertical` sibling (to the right). — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Commands, registered only when `canSplit` (`!S.isPhone`): `workspace:split-vertical` is named `w.commands.splitRight()`, icon `lucide-separator-vertical`, and calls `duplicateLeaf(activeLeaf, "vertical")` for an editor view that is not in a sidebar. `workspace:split-horizontal` is named `w.commands.splitDown()`, icon `lucide-separator-horizontal`, and calls `duplicateLeaf(activeLeaf, "horizontal")` with no sidebar guard. The same pair is in the application menu as those two command ids. The leaf tab menu uses the same functions: `splitRight` then `duplicateLeaf(leaf, "vertical")` (disabled in the sidebar), and `splitDown` then `duplicateLeaf(leaf, "horizontal")`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `duplicateLeaf` treats a second argument of `"horizontal"` or `"vertical"` as the split direction and then calls `createLeafBySplit(leaf, direction)`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Drag uses the same mapping. On drop, `D = (top or bottom) ? "horizontal" : "vertical"`, then `splitLeaf(target, draggedLeaf, D, left or top)`. Center drop on a tab group does not split: it uses `getTabInsertLocation` and `insertChild` into that group. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `getDropDirection` treats the outer 33% of each edge as a split zone. The third argument is a denylist. For a normal tab group, the top zone is narrowed to the top third of the tab header; the rest of the header stays `"center"` (insert a tab). On a stacked group, if the pointer is not over the header container, `"left"` and `"right"` are added to the denylist, so dragging across the stacked panes does not create a vertical split. Bottom 33% can still return `"bottom"` (a horizontal split). — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Sidebar drag denylist, from the helper in `onDragLeaf`: if the target is the dock split (`Ro`), all four edges are denied (only center). If the target’s root is the left or right dock, `"left"` and `"right"` are denied and `"top"` / `"bottom"` remain. Dropping on the dock element itself does not call `splitLeaf`; it inserts the leaf into the first tab group, creating one if needed. A top or bottom drop on a sidebar leaf calls `splitLeaf` with `"horizontal"`, which matches the dock’s forced direction, so the new tab group is a sibling in that dock rather than a nested vertical split. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- The file menu item named `openToTheRight` calls `openLinkText(path, "", "split")`. `getLeaf("split")` is the API that means a new split. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Official docs also say the root split’s default direction is vertical, and a new leaf added to it becomes a new column. — [Workspace](https://docs.obsidian.md/Plugins/User+interface/Workspace)

### Inferences
- The API word matches the divider, and the UI word matches the screen direction. `"vertical"` / `mod-vertical` / `flex-direction: row` / command `workspace:split-vertical` / `splitRight` are one gesture. `"horizontal"` / `mod-horizontal` / `flex-direction: column` / `workspace:split-horizontal` / `splitDown` are the other.
- `before: true` is “left” for a vertical split and “above” for a horizontal split, because `splitLeaf` inserts at the current index when `before` is set and at `index + 1` otherwise.
- Drag-to-stack, in this app, means a center drop into a tab group that is already stacked (or that the user then stacks). It does not create `mod-horizontal`. Drag-to-split is an edge drop that calls `splitLeaf`. On a stacked group the left and right edges are suppressed so the usual sideways drag stays a tab insertion.
- `createLeafBySplit(leaf, "vertical")` does not consult the sidebar denylist. On a sidebar leaf whose parent dock is `horizontal`, that call nests a `mod-vertical` split under the dock. The drag gesture refuses that nest; the API does not.

### Gaps
- `openLinkText`’s body was not extracted, so it is not confirmed here that pane type `"split"` passes direction `"vertical"` rather than relying on the default. The menu around that call is named `openToTheRight`, and the default inside `splitLeaf` is `"vertical"`.
- Exact English labels for `splitRight()` and `splitDown()` are not stored as plain strings in this asar’s `app.js`.

## What happens on workspace load (root forced vertical, sidebars horizontal)?

### Takeaway
`setLayout` keeps whatever direction nested splits were saved with, then forces the root split to `vertical` and both sidedock splits to `horizontal` if the saved value differs, and renormalizes child percentages. Missing sections are created with those same directions. Popout window splits are constructed as `vertical`.

### Cited Findings
- Layout is read back in `setLayout`. For `e.main`, the result is assigned to `rootSplit`. If that node’s `direction !== "vertical"`, it calls `setDirection("vertical")` and `recomputeChildrenDimensions()`. For `e.left` and `e.right`, the force runs only when the node is a `Ro` sidedock and `direction !== "horizontal"`, then the same `setDirection("horizontal")` plus `recomputeChildrenDimensions()`. Floating layouts are deserialized with no direction rewrite in this function. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- If `main` did not produce a root, the fallback is `new A1(this, "vertical")`, which is a root split (`mod-root`) whose constructor direction is `"vertical"`, containing one new tab group and one empty leaf, then the last open file if it exists. If the left dock is missing, desktop builds `new Ro(this, "horizontal", "left")`. The right dock is `new Ro(this, "horizontal", "right")` and then `collapse()`. Mobile uses drawer objects instead of `Ro`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `deserializeLayout` for `type === "split"`: a root id builds `new A1(this, e.direction, e.id)` so the saved direction is applied first and the force in `setLayout` may then overwrite it. A left or right id on desktop builds `new Ro(this, e.direction, side, id)`, applies `e.width` through `setSize`, and `e.collapsed` through `collapse()`. Any other split is `new Jn(this, e.direction, e.id)`. After children exist, each child’s `dimension` is restored with `setDimension`, then `recomputeChildrenDimensions()` runs. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- A saved leaf whose parent is not `type === "tabs"` (and is not a mobile drawer) is wrapped in a new tab group before insert. So a leaf does not stay a direct child of a split across a reload. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- On phone (`!canSplit`), root deserialize gathers every `tabs` node in the saved tree, appends the later groups’ children into the first group, and replaces the root’s children with that single group. `canSplit` is false only when `S.isPhone`. This desktop install still contains that branch. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Popout windows are `bs`, constructed with `super(e, "vertical", i)` and classes `mod-root` and `workspace-window`. Their split direction is `"vertical"` at construction, not taken from a saved `direction` field in that constructor. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Saved file names in the bundle are `workspace.json` (`Doe`) and `workspace-mobile.json` (`Poe`), written under the vault config dir by `saveLayout`. `getLayout` stores `main` from `rootSplit.serialize()`, plus `left`, `right`, optional `floating`, and `left-ribbon`. Split `serialize` includes `direction`. Tab `serialize` includes `currentTab` when greater than 0 and `stacked: true` when stacked. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- The startup splash DOM is built with the same classes the live root uses: `workspace-split mod-vertical mod-root mod-visible` containing `workspace-tabs mod-active mod-visible mod-top` containing `workspace-tab-container` containing `workspace-leaf mod-active`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- The public docs say the root split direction defaults to vertical, and that a new leaf in it creates a column. They also say a side-dock split’s direct children are tabs, with a depth of three. — [Workspace](https://docs.obsidian.md/Plugins/User+interface/Workspace)

### Inferences
- The force is only the outermost root node and the two dock nodes. A horizontal split nested inside the root survives load. A plugin that saves `main.direction: "horizontal"` will see that root flipped back to `vertical` on the next `setLayout`, and its child percentages recomputed.
- After the flip, `setDirection` swaps `mod-horizontal` for `mod-vertical` on that one element. Child `width: 0` rules replace `height: 0` rules. Calling `recomputeChildrenDimensions` does not by itself change the axis; the class change does.
- The docs’ “sidebars only contain tabs” matches the drag denylist and the load-time leaf wrapping. It does not match an unconditional `createLeafBySplit(..., "vertical")` inside a horizontal dock, which nests a vertical split under the dock and will still be there after the next load, because the horizontal force does not walk descendants.

## Which DOM or CSS changes are known to collapse stacked panes or force every split into one direction?

### Takeaway
Stacked panes collapse when CSS puts them back on `flex: 1 0 0`, sets their width to 0, changes `position: sticky`, or sets `display: none` on non-active leaves. Every split is forced to one axis by `setLayout` (root vertical, docks horizontal) or by a stylesheet that overrides `.workspace-split`’s `flex-direction` while leaving the `width: 0` / `height: 0` rules tied to `mod-vertical` / `mod-horizontal`.

### Cited Findings
- Stacked children are `flex: 0 0 auto; position: sticky` only under `.workspace .mod-root .workspace-tabs.mod-stacked .workspace-tab-container > *`. The general rule `.workspace-tab-container > * { flex: 1 0 0 }` is what non-stacked leaves use. A later or `!important` rule that restores `flex: 1 0 0` on those children removes the stacked override. Basis 0 with grow 1 makes the headers and leaves share the row instead of holding `--tab-stacked-pane-width` (700px) and the header width. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Stacked leaf width is `width: var(--tab-stacked-pane-width)` and the JS also sets inline `minWidth`, `maxWidth`, and `left`. Forum users set `body { --tab-stacked-pane-width: 100%; }` (or 98%) so each pane fills the group and the neighboring sliver disappears. Another snippet sets `position: inherit` on `.workspace .mod-root .workspace-tabs.mod-stacked .workspace-tab-container > *`. The poster wrote that the property “usually is `position: sticky`” and that sticky is what enables the overlapping panes. — [Forum: full-width stacked tabs](https://forum.obsidian.md/t/tab-stacks-sliding-mode-add-option-to-show-only-one-tab-a-time-with-two-collapsed-stacks-on-the-sides-full-width-tab/45036?page=3)
- Offscreen stacked leaves stay in the document. Only `.workspace-leaf.is-hidden > * { display: none }` runs, and only inside the root stacked container. A rule such as `.workspace-split .workspace-leaf:not(.mod-active) { display: none }` removes the other panes from the flex row. A published snippet does that for leaves whose `style` attribute is empty, sets the active leaf to `flex-basis: calc(100% - 4px) !important`, and then the author adds a separate rule to put sidebar leaves back, describing the first rule as breaking sidebars. — [Reddit: maximize active stacked tab](https://www.reddit.com/r/ObsidianMD/comments/1gtsjlv/css_to_maximize_active_editor_in_stacked_tabs/); [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `updateTabDisplay` moves headers into `.workspace-tab-container` in stacked mode and moves them back to the header strip otherwise. The stacked header rule sets `writing-mode: var(--tab-stacked-text-writing-mode)` and a fixed `width: var(--tab-stacked-header-width)`. Putting those headers back into `.workspace-tab-header-container`, or setting the stacked tab container to `flex-direction: column`, lays the sliding panes out on the wrong axis. The container rule that stacked mode replaces is `display: flex; flex-direction: row; overflow-x: auto; overflow-y: hidden`. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar); [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Direct split children are zero on the main axis: `mod-vertical > *` has `width: 0`, `mod-horizontal > *` has `height: 0`, both with `flex: 1 0 0`. Applying `width: 0` to horizontal children, or `height: 0` to vertical children, or applying both zeros to `.workspace-leaf` (a descendant, so the stacked width rule is the one that gives the leaf a size), collapses that axis. Leaves also have `contain: strict !important`. Removing containment lets content min-size fight the zero main size of the split child. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- `.workspace-split.mod-vertical { flex-direction: row }` and `.workspace-split.mod-horizontal { flex-direction: column }` are the only direction rules. An author stylesheet that sets `.workspace-split { flex-direction: column }` or `row` on every split makes both classes look like one axis, while `width: 0` still applies only to `.mod-vertical > *` and `height: 0` only to `.mod-horizontal > *`. A vertical split forced into a column keeps `width: 0` on its children, so those children have a zero main size for a row and a zero cross size for a column. Resize still reads `offsetWidth` or `offsetHeight` from the JS `direction`, which `setDirection` keeps in sync with the class and a manual class toggle does not. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar); [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Load already forces one direction at the roots: root becomes `vertical`, both `Ro` docks become `horizontal`, and child dimensions are recomputed. Nested splits are left as saved. See the load section. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)
- Docks are `flex: 0 0 auto` with an inline pixel width. The main-split child rule `flex: 1 0 0; width: 0` is what fills the editor. Putting that rule on `.mod-primary-split` or `.mod-secondary-split` replaces the dock’s `flex: 0 0 auto`. Collapsed docks set inline width `0` and the class `is-sidedock-collapsed`. — [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar); [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)

Mobile CSS also has `.is-phone .mod-root .workspace-split:not(.mod-visible),.is-phone .mod-root .workspace-tabs:not(.mod-visible){display:none}`. Stripping `mod-visible` on mobile hides those nodes. That branch is in this desktop build’s CSS and JS; `canSplit` is true on desktop. — [obsidian.asar app.js](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar); [obsidian.asar app.css](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)

### Inferences
- The safe plugin surface is the workspace API (`createLeafBySplit`, `setStacked`, `setDirection` / the split’s own direction) plus layout data (`dimension`, `stacked`, `direction`). The unsafe surface is rewriting `flex`, `width`, `height`, `flex-direction`, or `display` on `.workspace-split`, its direct children, or `.workspace-tab-container > *`.
- Stacked mode and split direction fail in different places. Breaking `position: sticky` or `--tab-stacked-pane-width` changes one tab group’s sliding row. Breaking `mod-vertical` / `mod-horizontal` or the `width: 0` / `height: 0` pair changes every pane in that split.
- Toggling `mod-vertical` on the DOM without `setDirection` leaves `this.direction` on the old axis, so the next drag writes `width` when the CSS is reading the column, or the reverse.

### Gaps
- No theme or plugin stylesheet from this vault was measured in a running Obsidian window. The collapse cases above are the installed CSS rules plus the two public snippets that users already use to flatten stacked panes. A live layout was not screenshotted.
