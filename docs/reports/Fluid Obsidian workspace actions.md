# Make Working Tabs follow native splits

Working Tabs stays aligned with Obsidian’s splits and stacked tabs when each live group is the tab group a leaf already belongs to, and when Open, drag, Hide, and Focus either invoke one host placement verb or only record the tree Obsidian has just changed. In the installed 1.15.1 desktop app, **Split right is direction `"vertical"`** (class `mod-vertical`, children in a row, main-axis size `width: 0`) and **Split down is `"horizontal"`** (class `mod-horizontal`, children in a column, main-axis size `height: 0`); **stacked tabs are `setStacked` on that same tab group**, class `mod-stacked`, a sliding row inside one group ([obsidian.asar](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)). The plugin fights that model on the gestures people repeat. Default open mode `'tab'` **calls `createLeafBySplit` with `'vertical'` whenever the active pane is already claimed**, so a click that reads like a new tab is an unlabeled split right. Focus and Hide set **`display: none` on `.workspace-tabs` and on any ancestor split whose panes are all hidden**, pulling flex items out of a tree whose children are `flex: 1 0 0` with a zero main size. The workspace drop overlay uses **25% edge bands and a center “Merge into” target**, while Obsidian’s own drag splits only in the outer **33%** of an edge and treats the center as an insertion into the tab group ([TabSpacesView.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/views/TabSpacesView.ts), [obsidian.asar](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar)). Vertical Tabs creates a split only when the user asks for a new group, and Pane Relief only reorders leaves that already exist; the `display: none` stylesheets in both are the bug trackers for missing toggles and unreachable sidebars, and classic Sliding Panes’ inline flex is what leaves stacked tabs broken after that plugin is disabled ([Pane Relief README](https://github.com/pjeby/pane-relief/blob/master/README.md)). The redesign is the menus already on the row: a dormant Open offers **Split right, Split down, Move into current tab group, and Open in new window**; a live row only reveals; a pane leaves by **Close** (`detach`); Focus filters the sidebar and reveals live groups; **Stack tabs** toggles the existing group from More; the overlay is deleted; reconcile keeps recording and is no longer asked to explain a tree the sidebar just restyled.

## A stack slides inside one tab group

Obsidian lays the workspace out as splits of tab groups, and a plugin that wants to feel native has to keep those two objects distinct. A split places its children one after another on a single direction. A tab group shows one child leaf at a time and hides the others, unless that group is stacked. The root and both side docks are splits; a side dock’s children are tab groups, and those tab groups contain the leaves. In this plugin’s own vocabulary a **pane** is `leaf.parent`, that tab group, in the main area, and a **group** is a stored node that claims at most one pane through `homePaneId`. The claim records which pane that is. Sizing stays on the split. ([Workspace](https://docs.obsidian.md/Plugins/User+interface/Workspace))

The direction words name the divider, and the CSS main axis runs the other way across the screen. A split is `.workspace-split`. **`mod-vertical` is `flex-direction: row`**, and each direct child is `height: 100%; flex: 1 0 0; width: 0`. **`mod-horizontal` is `flex-direction: column`**, and each direct child is `width: 100%; flex: 1 0 0; height: 0`. Those rules apply only to direct children, which are nested splits or tab groups. The zero length is the main axis, so content cannot force a pane open; `flex: 1 0 0` is grow 1, shrink 0, basis 0. The stored size is a percentage on inline `flexGrow`. `setDimension` stores `null` when the value is `<= 0` or `>= 100`, and if any child is `null`, `recomputeChildrenDimensions` clears every sibling to an equal share. During a divider drag the sizes become pixels with `flex: 0 0 auto`, the drag refuses to shrink a child below **200px**, and `finishResize` clears the inline pixels and writes the ratio back through `setDimension`. A plugin that reapplies pixel `width` or `height` on every layout change is sitting on the temporary resize channel and pinning the panes after Obsidian has already returned them to percentages. ([obsidian.asar](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar))

The public API matches the screen, and the class matches the divider. **`getLeaf('split')` with `'vertical'` places the new leaf to the right; `'horizontal'` places it below.** `createLeafBySplit` builds a leaf, wraps it in a new tab group, and nests a new split only when the requested direction differs from the parent. The omitted direction defaults to `"vertical"`, so a call with no direction is Split right. Commands follow the same pair: `workspace:split-vertical` is Split right, `workspace:split-horizontal` is Split down. On load, `setLayout` **forces the root split back to `vertical` and both side-dock splits to `horizontal`**, then renormalizes child percentages. Nested splits keep the direction they were saved with. A saved `main.direction` of `"horizontal"` is flipped on the next layout, and the child rule swaps from `height: 0` to `width: 0` because `setDirection` swaps the class. Popout windows are constructed as `vertical`. The horizontal force on a dock does not walk descendants, so a vertical split nested under a dock by an API call survives reload even though a drag onto that dock refuses left and right edges. ([Workspace reference](https://docs.obsidian.md/Reference/TypeScript+API/Workspace), [createLeafBySplit](https://obsidian-typings.github.io/obsidian-typings/public/api/obsidian/augmentations/Workspace/createLeafBySplit/))

Stacked tabs are a mode of one tab group, which is the distinction the plugin’s direction comment currently collapses. The comment in the view treats `'horizontal'` as “stacked” and labels it Split down. **`setStacked(true)` adds `mod-stacked`, shows every leaf, and moves each tab header into the scrolling row beside its leaf.** Serialization writes `stacked: true` only when that flag is set. The stylesheet that makes the panes slide is scoped to `.workspace .mod-root .workspace-tabs.mod-stacked`: the tab container becomes a horizontal scroller, its children become `flex: 0 0 auto` and `position: sticky`, and each leaf’s width is **`--tab-stacked-pane-width`, default 700px**. Offscreen leaves stay in the flex row; `is-hidden` hides their children, not the leaf box. The command `workspace:toggle-stacked-tabs` and the tab-list menu both refuse the side docks. `canStackTabs` is false on phone, and `setStacked` then forces false. A horizontal split remains the other object: several tab groups in a column, each normally showing one leaf, with a resize handle between them. The 1.0.0 changelog states the same split of concepts: a tab stack is a way to view a tab group, and a tab group and a tab stack can sit side by side. Sliding panes, in this app, are `setStacked` on the leaf’s parent. The surrounding split direction stays untouched. ([setStacked](https://obsidian-typings.github.io/obsidian-typings/public/api/obsidian/augmentations/WorkspaceTabs/setStacked/), [Obsidian 1.0.0](https://obsidian.md/changelog/2022-10-13-desktop-v1.0.0/), [TabSpacesView.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/views/TabSpacesView.ts))

Those rules also name the CSS that collapses the layout. Stacked panes lose the slide when a later rule puts those children back on `flex: 1 0 0`, sets their width to 0, changes `position: sticky`, or sets `display: none` on non-active leaves. Published snippets do this on purpose: `body { --tab-stacked-pane-width: 100%; }` so each pane fills the group, `position: inherit` on the stacked children where the author notes that sticky is what overlaps the panes, or a rule that sets non-active leaves to `display: none` and then needs a second rule to put sidebar leaves back. Every split is forced onto one axis by a stylesheet that sets `flex-direction` on `.workspace-split` while `width: 0` stays tied to `mod-vertical` and `height: 0` stays tied to `mod-horizontal`. Toggling the class in the DOM without `setDirection` leaves `this.direction` on the old axis, so the next drag writes `width` while the CSS is laying out a column. The safe surface is the workspace API together with the layout fields `dimension`, `stacked`, and `direction`. ([Full-width stacked tabs](https://forum.obsidian.md/t/tab-stacks-sliding-mode-add-option-to-show-only-one-tab-a-time-with-two-collapsed-stacks-on-the-sides-full-width-tab/45036?page=3), [Maximize the active stacked tab](https://www.reddit.com/r/ObsidianMD/comments/1gtsjlv/css_to_maximize_active_editor_in_stacked_tabs/))

## Hide and focus remove flex items the split still measures

Working Tabs has already hit this mechanism once. The comment above the hide rules says an earlier version **forced `display: flex` on every nested split and broke the height chain**, so stacked panes collapsed on load and only the side-by-side panes remained. The shipped rules drop that override and do something narrower. On desktop, **`.workspace-tabs.working-tabs-hidden-pane` is `display: none`**, and a nested `.workspace-split` under `.mod-root` is `display: none` when it contains a hidden pane and no visible `.workspace-tabs`. `applyHiddenClass` toggles the class from `effectivelyHidden`, and reconcile reapplies it to every live group after every plan. The colour stripe is a `::before` with `pointer-events: none`. It sets `position: relative` on the tab group and does not set `display`, `flex`, or `flex-direction` on the split. The stripe can stay. ([styles.css](file:///D:/Repos/Obsidian/obsidian-tab-space/styles.css))

`display: none` takes a flex item out of the layout. The remaining children still carry `width: 0` or `height: 0` and grow by `flexGrow`. A fully hidden nested split disappears from its parent row, so a column of panes presents as a row of whoever is left. The leaves stay in the workspace and in the snapshot, so the sidebar still treats the group as live while the split tree is missing a child. Showing the pane again only drops the class. It does not ask Obsidian to recompute `dimension`. The “panes end up vertical on load” picture was not reproduced in a running window in this research. Two mechanisms in the loaded tree can produce it: persisted hide and focus classes applied on the next reconcile, and unlabeled `createLeafBySplit(..., 'vertical')` from open. Which one a given vault hits was not observed. How `detach` redistributes `dimension` was not measured either. ([leaf-sync.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/leaf-sync.ts), [membership.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/membership.ts))

Focus is that hide rule with a wider predicate. **`effectivelyHidden` is true when the group is hidden, when its section is hidden, or when `focusedSectionId` is set and the group’s parent is a different section.** A root group, whose parent is null, is hidden whenever any section is focused. The crosshair and the section menu only write `focusedSectionId`. The store listener’s `refreshHidden` paints the panes, including collapsing any split that no longer contains a visible tab group. The sidebar, separately, renders other sections collapsed and moves the focused section to the top of the list. That list behavior is chrome. The workspace behavior is a visibility tree reapplied on layout change, and it also decides where new panes are filed: an unclaimed pane becomes a group parented under `focusedSectionId`. The installed command table uses “Focus on tab group to the left,” “below,” and “to the right” for moving attention between tab groups that remain on screen. ([obsidian.asar command strings](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar), [membership tests](file:///D:/Repos/Obsidian/obsidian-tab-space/src/membership.test.ts))

A second chrome rule fights the host’s hit testing. **`working-tabs-hide-tab-headers` sets `.mod-root .workspace-tab-header-container` to `display: none`.** Native drop testing reads that header’s box. On an unstacked group the header locks the result to center, except the top third of the header height, which is a split upward. With the header at `display: none` there is no box that distinguishes that split from moving into the tab group, and the native “+”, close, and tab-drag targets are gone. The settings copy already points at the group menu’s New tab as the replacement. Stack tabs lives on that same header menu. The header row is part of the placement language, and the hide-tab-bar setting is a separate fight from Hide pane. Leaving the header row visible is what keeps Split up, tab insertion, and Stack tabs aimed at a real target. ([styles.css](file:///D:/Repos/Obsidian/obsidian-tab-space/styles.css), [settings.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/settings.ts))

The maintained peers have already paid for this class of rule. Vertical Tabs’ zen stylesheet sets **`display: none` on inactive `.workspace-tabs` and on nested `.workspace-split`**, then `display: flex` on a split that still contains a visible tab group or that contains no `.workspace-tabs` at all. The stylesheet comments name the exceptions: empty containers, and Excalidraw embeds plus other plugin containers. In November 2024 a desktop user saw Split pane show up only as another copy in the sidebar; the maintainer’s diagnosis was that zen mode was hiding the inactive splits, and turning zen mode off brought the panes back. Pane Relief’s maximize mode applies the same `display: none` to splits that do not contain the maximized leaf. Release 0.5.0 had hidden the main area when a sidebar leaf was active, and it had broken dragging at the top of a non-native frame. Release **0.5.9, on 22 February 2025**, fixed right-sidebar tabs that could not be reached while maximized or in sliding panes, after earlier releases had to recreate a view-header drag icon Obsidian 1.6 had removed. Hiding `.workspace-tab-header-container` forced both plugins to paint sidebar toggles and the frameless `-webkit-app-region` drag strip back by hand. An `is-hidden` class that is not part of the workspace layout also fails to round-trip: Vertical Tabs issue #101, in January 2025 on Obsidian 1.8.0, was an empty left-sidebar tab strip that appeared only after restart. ([ZenMode.scss](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ZenMode.scss), [Issue #57](https://github.com/oxdc/obsidian-vertical-tabs/issues/57), [Pane Relief 0.5.9](https://github.com/pjeby/pane-relief/releases/tag/0.5.9), [Issue #101](https://github.com/oxdc/obsidian-vertical-tabs/issues/101))

Hide stops writing workspace CSS. The `display: none` rules on the hidden pane and on the ancestor split come out. Putting a pane away is the existing Close group path: **`detach` every leaf in the pane, clear `homePaneId`, and keep the stored tabs** so Obsidian recomputes the split. The eye buttons and “Hide all groups in this section” leave with those rules, because they are a second layout engine beside `detach`. Focus keeps the host’s meaning, which is attention. Focusing a section expands it in the list, reveals the live tab groups already in it, and stops feeding `focusedSectionId` into `effectivelyHidden`. The chevron already folds the list. On phone the hide selector does not match, because it is guarded with `body:not(.is-phone)`, and the host already refuses stacking there. The desktop rules are the ones that fight the flex tree.

## Open and the center drop invent a second placement language

The open path already contains a correct menu and a fallback that undoes it. The New group row offers Split right, Split down, and New window. Its comment says mode `'tab'` is omitted because a tab-mode new group would fall into the active pane and join that pane’s group. The dormant Open menu then adds **“New tab” (`{ mode: 'tab' }`)** and **“Open in current pane (merge)”**. After any choice on that menu, `setOpenBehavior` stores it as the row-click default. Every auto-created group is born with **`{ mode: 'tab' }`**, and the settings screen never edits the global default. Row click, Enter, and the section item **Open all** call `openGroup` with no override, so they inherit that default. A live group’s row click is the one path that only reveals. ([TabSpacesView.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/views/TabSpacesView.ts), [types.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/types.ts))

Mode `'tab'` is an unlabeled split right as soon as the workspace is in normal use. The function comment says the mode reuses an unowned active pane, otherwise splits, and never merges. **When the most recent leaf’s pane is already claimed, `createLeafForOpen` calls `createLeafBySplit(active, 'vertical')`.** Once any group is live, the usual main pane is owned, so row click, Enter, Open all, and New tab on a dormant group with the default behavior all split right. Open all fires one `openGroup` per dormant child without awaiting, and each call reads `getMostRecentLeaf()` at its own moment. The README line that says opening into an occupied pane merges does not match this branch. The unowned branch is a different surprise: it appends one leaf with `createLeafInParent` and then `setHomePane` on that whole pane, so the next reconcile can absorb the pane’s other leaves into the group with no merge receipt. ([leaf-sync.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/leaf-sync.ts), [README.md](file:///D:/Repos/Obsidian/obsidian-tab-space/README.md))

The same hard-coded direction sits on moves that the menus describe as grouping. **“Move to new group” always calls `createLeafBySplit(anchor, 'vertical')`.** Undo of a merge always splits the target to the right and reopens whatever saved tab records still exist; it does not restore the geometry from before the merge. “Move to: {title}” is offered for every other group, completed groups included. Into a group that has no live pane, `moveTab` updates the record and returns, **leaving the open leaf where it was**. The next `layout-change` or the 3-second poll sees the key still living in the old pane while the record’s parent is dormant, which is the plan branch that `addTab`s a second copy onto the live group and keeps the dormant list. Opening a completed row has a cousin of that bug. Completed groups are omitted from `plan()`, but the row still calls `openGroup`, which creates leaves and claims a pane. The following pass sees an unclaimed pane and emits a new group plus new tab records, beside the completed copy the planner is written to ignore. ([leaf-sync.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/leaf-sync.ts), [membership.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/membership.ts), [membership.test.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/membership.test.ts))

The workspace overlay paints a second drop language on a direction map that already matches `splitLeaf`. Edge drops call `createLeafBySplit` with `'horizontal'` for top and bottom, `'vertical'` for left and right, and `before` for top and left. The hit areas are the plugin’s. **A 25% band on each edge, with `y` tested before `x` so every corner is top or bottom, frames a center box inset 10%** whose text is `Merge into ${title}` and whose drop calls `mergeGroupInto`. ([TabSpacesView.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/views/TabSpacesView.ts), [styles.css](file:///D:/Repos/Obsidian/obsidian-tab-space/styles.css)) Native `getDropDirection` starts at center and lets an edge win only when its fractional distance is **under 0.33** and nearer than the current winner. On an unstacked tab group, a pointer over the header sets the running distance to zero so later edges cannot win; the top third of the header height is a split up, and the rest of the header is center. On a stacked group, left and right are removed when the pointer is outside the header, so a sideways drag across the note stays a tab insertion and the bottom 33% can still split downward. Center preview is the tab-slot rectangle from `getTabInsertLocation`, and the drop `insertChild`s into that group. Help describes the highlight the same way: when only the tab area of a group lights up, the dragged tab joins the tabs already there. ([obsidian.asar](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar), [Sidebar](https://obsidian.md/help/sidebar), [Tabs](https://obsidian.md/help/tabs))

A live group dropped on an edge is a harsher mismatch than the rectangle. **`openGroupAtDropTarget` calls `closeGroup` first when the group is already live, detaching every leaf and clearing `homePaneId`, then splits and reopens from stored view state.** That deletes a flex child and inserts a new split. The host drag does the same gesture as one `splitLeaf` or one `insertChild`. The in-place move the plugin already has is the pattern to keep for a tab that is open: `relocateLiveLeaf` calls `removeChild`, `insertChild`, optional `selectTabIndex`, and `requestResize`, and it returns without moving if those methods are missing. There is no public API in this repo that draws `workspace-drop-overlay`. A faithful drop copies the threshold rules and calls `createLeafBySplit` or `createLeafInParent`. Handing the gesture to Obsidian’s private drag manager was read out of the install and was not verified as a plugin call. ([leaf-sync.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/leaf-sync.ts), [obsidian.asar](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar))

The word “merge” is also doing work the host names differently. `mergeGroupInto` returns immediately when no group’s pinned `homePaneId` equals the target, and the Open-menu item passes **raw `parent.id`**. The plugin pins ids precisely because `leaf.parent.id` “can churn across splits and drags,” so the menu path can miss the owner and change nothing, while the center drop looks the owner up with the pinned id and builds the label from the raw id. When the merge does run, it detaches the source pane, moves the restorable records, reopens them at the end of the target, deletes the source group, and shows Undo. That behavior is the host’s center drop: insert these leaves into this tab group. Searches of the 1.15.1 command and menu tables found **“Split right,” “Split down,” “Toggle stacked tabs,” “Stack tabs,” “Unstack tabs,” “Open in new window,” and “Move to new window.”** They found no “Move to this tab group,” no “Split left,” and no “Split up.” The Help extract calls the stack item “Stack notes.” This install’s menu strings are the naming source for the plugin, and they say Stack tabs. ([obsidian.asar command strings](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar), [Tabs](https://obsidian.md/help/tabs))

One anchor bug sits under every menu split. Placement uses `getMostRecentLeaf()` and does not apply the filter the snapshot uses, which skips `leftSplit`, `rightSplit`, and the Working Tabs view. Whether a sidebar click actually makes that leaf the most recent one was not observed in a running app. The API consequence is already visible in the install: `createLeafBySplit(leaf, "vertical")` does not consult the drag denylist, so on a leaf whose dock is horizontal it nests a `mod-vertical` split under the dock, and the next load keeps that nest because the dock’s horizontal force does not walk descendants. Pane Relief’s navigation already substitutes `getMostRecentLeaf(rootSplit)` when the active leaf’s root is a side dock, for the related reason that sidebar tabs were stealing focus. Menu splits belong on the most recent leaf whose root is the root split. ([leaf-sync.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/leaf-sync.ts), [obsidian.asar](file:///D:/Users/grego/AppData/Local/Programs/Obsidian/resources/obsidian.asar), [pane-relief.ts](https://github.com/pjeby/pane-relief/blob/master/src/pane-relief.ts))

## Maintained sidebars mirror the saved tab group

Vertical Tabs, the sidebar that actually lists open editor tabs, treats each native tab group as the thing in the list. The feature tour, dated 17 October 2026, says a tab group is the workspace split Obsidian already persists, so install, uninstall, reload, and restart keep the same layout, and dragging groups does not rewrite the overall layout because the groups are ordered the way the workspace is. **“New group” is `getLeaf("split")` plus `openFile`.** “Open file in tab group...” splits, opens the file, and moves that tab to the end of the new parent. Moving between groups uses the parent’s own methods: `removeChild`, `leaf.setDimension(null)`, `insertChild`, `selectTabIndex`, `requestResize`. A new group made from an existing tab is `duplicateLeaf(source, "split", direction)` and then `source.detach()`, with `"horizontal"` when the source element is taller than it is wide and `"vertical"` otherwise. On phone, where `Platform.canSplit` is false, those calls run inside a reference-counted patch that restores the flag in `finally`. The author, on 6 November 2024, told a user who wanted one group to contain tabs from different panes that the design exists to stay in sync with the native UI, and that groups arranged as panes were necessary for that. A parallel Session, then Group, then Section hierarchy was described as future work. The October 2026 tour does not document a Session object. ([Feature tour](https://vertical-tabs-docs.oxdc.dev/User-Guide/feature-tour), [Discussion #60](https://github.com/oxdc/obsidian-vertical-tabs/discussions/60), [MoveTab.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/MoveTab.ts))

Their extra view modes show the boundary between a presentation and a new split. Continuous, column, and Mission Control are CSS classes on the existing group. **`setGroupViewType` calls `setStacked(false)` for every type, including the default,** and the multi-leaf modes then append each leaf element onto the tab container in `children` order. The CSS forces every `.workspace-leaf` to `display: block !important` and `contain: unset !important`, and it turns the tab container into a column, a row, or a grid. Doing that CSS while native stacking is still on, or while the DOM order disagrees with `parent.children`, is how the picture and the workspace array diverge. Zen mode is the step past presentation into hide-the-tree, and it is where issue #57 and the embed exceptions live. Working Tabs has no need of those view modes. The part worth copying is the order of operations: turn the host’s stack off before showing every leaf, and keep the DOM order equal to the child list in the same turn. Shipping a Session layer on top of tab groups is the parallel hierarchy the author left as future work in November 2024, and the October 2026 tour still does not document it. ([VTGroupView.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/models/VTGroupView.ts), [Continuous view styles](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/styles/ContinuousView.scss))

Pane Relief is the smaller instrument, and its limits are instructive. Move commands **only reorder `leaf.parentSplit.children` of the active leaf**. Swap is a relative index. “Place as nth tab in group” is an absolute index in that same child list, which is easy to misread as a window-wide slot. If the parent has `selectTab`, the command splices and selects; otherwise it also moves the DOM node and calls `recomputeChildrenDimensions`, `onResize`, and `onLayoutChange()`. Cycle and jump walk leaves that already exist and then `setActiveLeaf`, substituting the most recent root-split leaf when focus is in a sidebar. Maximize toggles `should-maximize` and refreshes classes. It does not remove leaves. Sliding mode toggles `is-sliding` per window, scrolls the active tab group into view, and persists the class across restart. After Obsidian 0.16 it **reads `isStacked` and widens the group by `--tab-stacked-header-width` times the tab count**. The README says this replaces classic Sliding Panes’ stacking and header rotation, which “are now supplied natively by Obsidian 0.16.2,” and it still calls sliding panes beta because scrolling can be jumpy when a stack does not fit the window. Issue #52, still open, asks for functions that move tabs to other groups. Issue #64, opened 19 February 2025, reports that close-and-go-adjacent lands focus on the right-hand group. The verbs a user sees are jump, place, swap, cycle, maximize, and toggle sliding panes. ([pane-relief.ts](https://github.com/pjeby/pane-relief/blob/master/src/pane-relief.ts), [Pane Relief README](https://github.com/pjeby/pane-relief/blob/master/README.md), [Pane Relief issues](https://github.com/pjeby/pane-relief/issues))

Classic Sliding Panes is the layout-owning counterexample those two were written against. On resize, and after layout ready, it reads `rootSplit.children` and assigns inline **`flex`, `width`, `left`, and `right`**, and it replaces `onChildResizeStart` on the root split. Disabling is supposed to clear the inline styles and restore the resize hook. Pane Relief’s README says the plugin must be disabled and Obsidian restarted, because the hooks survive disable and then interfere with stacked tabs and with Pane Relief’s own sliding mode. A forum report after install and uninstall describes panes that could not be width-dragged and tabs that could not sit side by side. A reply there notes that native stacked tabs have no pointer resize and that width is the 700px variable. The thread does not include a maintainer confirming leftover hooks in that particular vault, so the restart warning stays pjeby’s report plus the resize code that is still in Sliding Panes’ `main.ts`. The inference that does follow is that writing `flex` and `width` onto root children is a failure mode of its own, in the same family as `display: none` on `.workspace-split`. It is not a gentler version of hiding. ([sliding-panes main.ts](https://github.com/deathau/sliding-panes-obsidian/blob/master/src/main.ts), [Cannot resize tabs](https://forum.obsidian.md/t/cannot-resize-tabs/66097))

The load-time rule falls out of those bugs. During `layout-change`, `resize`, and workspace load, the sidebar rebuilds its list from the tree Obsidian just finished. Vertical Tabs’ visibility helper returns without touching `leftSplit` or `rightSplit` when either is null “on layout reload.” Registering a custom view inside `onLayoutReady` replaces a restored leaf with `EmptyView`; a March 2026 forum report found `getLeavesOfType` empty for a view that had been open before quit, and the fix given was `registerView` in `onload`, before the layout is applied. Calling `workspace.onLayoutChange()` from inside a move re-enters every listener, which Vertical Tabs’ move-to-end path does. Working Tabs’ reconcile already matches the safe half: it listens to `layout-ready`, to every `layout-change`, and to a poll, and `applyPlan` only writes the store. Creating a leaf, detaching one, patching `Platform.canSplit`, or writing `display` in that same turn is the half the peer bugs keep punishing. A user command is the place a split is allowed to happen. ([Custom views not detected](https://forum.obsidian.md/t/bug-custom-views-are-not-detected-while-opening-obsidian-in-onlayoutready-callback/112337), [HorizontalTabVisibility.ts](https://github.com/oxdc/obsidian-vertical-tabs/blob/master/src/services/HorizontalTabVisibility.ts))

The vocabulary rule is the same constraint in the user’s language. Nielsen’s consistency heuristic says people should not have to wonder whether different words or actions mean the same thing, and that time in other products sets the expectation; the “match the real world” heuristic says to use the words the user already has. Instrumental interaction treats a command as an instrument on an object that is already on screen, and asks that the same instrument apply wherever that object appears. Here the object is the tab group. A live group in the sidebar means `leaf.parent`. A new group means a split. A stack means `setStacked`, which Vertical Tabs explicitly turns off before its own multi-leaf views. A sidebar heading that is not one of those parents drifts as soon as the user drags a native tab, reloads, or disables the plugin. That drift is the failure the Vertical Tabs author refused in November 2024. ([Consistency and standards](https://www.nngroup.com/articles/consistency-and-standards/), [Ten usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/), [Instrumental interaction](https://doi.org/10.1145/332040.332473))

## The row menus already hold the host verbs

The UI change is the menus that are already on the row. One Open button remains on a dormant group, and its menu is the whole placement UI: **Split right, Split down, Move into current tab group, and Open in new window**. Clicking the dormant row, or pressing Enter on it, opens that same menu. A live row click stays `revealLeaf` only, so the Open button stays off live rows. The New group row becomes Split right, Split down, and Open in new window. That row already creates one empty leaf and lets the next reconcile name it “Group N.” Only the window label changes, from “New window” to the host’s “Open in new window.” “Move to new window” stays reserved for a tab that already exists and is actually moving into a popout. This menu map was read from the plugin source and the installed strings. It was not clicked through in Obsidian.

Stack tabs joins the live group’s More menu and nowhere else. The item reads **Stack tabs** or **Unstack tabs** according to whether that pane’s tab group already has `mod-stacked`, and it toggles `setStacked` on that group once the group is the active tab group, so `workspace:toggle-stacked-tabs` has the parent the command requires. The command is registered only when stacking is allowed, and both the command and the header menu already refuse the side docks. The item stays off the dormant Open menu, because a dormant list has no tab group to stack, and it is not a fifth way to open beside Split down. It is not a row icon. The row does not grow a new layout control. The repo has no stack flag today. The class on `.workspace-tabs` is the installed signal, and this research did not find a plugin API field for it in the checkout. The archive slice used for the command body was truncated, so it is confirmed that the id, the label “Toggle stacked tabs,” and the menu pair exist, and it is not confirmed from that slice alone that the command always toggles `activeLeaf`’s parent. Aiming `setStacked` at the group’s own parent avoids depending on that.

The rest of More shrinks to the same verbs. The tab menu replaces **Move to new group** with Split right and Split down, each moving that one tab through `createLeafBySplit` in the direction the label names. **Move to {title}** lists live groups only, and an already-open leaf goes through `relocateLiveLeaf` into that tab group. A dormant title is a filing in the list, and the leaf stays in its pane until the user picks a verb that creates or fills a tab group. Close group keeps a distinct label. The host sentence “Close this tab group” does not leave a dormant list behind, so reusing it would make one phrase mean two outcomes. Undo last merge stays, and the reopen beside the target is labeled as the Split right the code already hardcodes with `'vertical'`. **Open all** leaves the section menu. Each dormant group needs its own placement, and the current loop calls `openGroup` with none, concurrently. **Close all** can remain as repeated `closeGroup`. New tab stays on a live group’s menu, where it is `createLeafInParent` at the end of that pane and an empty view. It leaves the placement menu, where mode `'tab'` falls through to a vertical split. The eye, the crosshair, Hide all, and Focus and Unfocus leave the section and group rows. The chevron already folds the list. Any control that keeps the word Focus reveals that section’s live tab groups with `revealLeaf` and leaves every other pane on screen.

Sidebar drag stays a list. Before, after, and into keep refiling sections and groups in the store, and a tab dropped on a live group still uses `relocateLiveLeaf` so the tab strip and the stored order move together. A tab dropped on a dormant group updates the record only while that leaf is closed. An open leaf stays with its pane, which closes the path where the catalog moves and the next reconcile `addTab`s a duplicate because the leaf never did. `registerWorkspaceDropZones` and the `working-tabs-pane-drop-*` rules go away, including the center sentence. Users who want a split see the verb in the Open menu, the same verb as the tab context menu on the workspace. A later drop of a dormant group, built on those same four verbs, can copy `getDropDirection` directly: center by default; an edge only inside 0.33 and only when it is nearest; the header is center except the top third of its height; top and bottom pass `'horizontal'`; left and right pass `'vertical'`; left and top pass `before: true`; a stacked group grows no left or right split from a drop on the note body; center inserts into that tab group and does not close anything. That drop is how the zones become faithful. The menus are how the verbs become obvious, and they ship first. The exact rectangle math inside `getTabInsertLocation` was not extracted, so a copied center hit inserts into the group and does not pretend to reproduce the slot highlight pixel for pixel.

Reconcile stays the recorder, with one identity fix so a native drag does not fork the catalog. On load, on `layout-change`, and after a native drag, the plan claims a pane that is already there, releases a pane that is gone, files tabs under the group that owns that pane, and creates a group record for an unclaimed pane. It does not call `createLeafBySplit`, `detach`, or a `display` change. The gap is the empty pane the planner’s merge step expects and the snapshot never produces. **`snapshot()` fills its map only from leaves, so a pane with zero leaves is absent, and the tested `merged` step does not run on the shape production actually emits.** Dragging every leaf out of a pane therefore releases the source, keeps it as a dormant list whenever any non-blank tab remains, and `addTab`s fresh records on the destination, because the source is no longer a live group and the in-place `moveTabRecord` branch never sees both ends. Dragging one tab between two panes that both survive already moves the record in place and keeps its node id. That is the branch to extend: when a claimed pane disappears and its keys are all present in one remaining pane, record a move and drop the empty source the way the merge receipt intends. Whether Obsidian leaves an empty leaf behind, which would keep the source pane in the snapshot and let the existing merge step run, was not observed in a running app. The recommendation follows from `snapshot()` and the plan. New panes are filed under `focusedSectionId` today because a focused section’s hide rule would otherwise hide the split the user just made. Once focus leaves the workspace CSS alone, filing a new group under a section happens when the user drops that group onto the section. ([leaf-sync.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/leaf-sync.ts), [membership.ts](file:///D:/Repos/Obsidian/obsidian-tab-space/src/membership.ts))

Saving `openBehavior` remains sound after the user picks Split right, Split down, or Open in new window. Saving mode `'tab'` after a silent vertical fallback records a placement the label did not show. That mode leaves the stored default. The calls that remain are the ones the host already documents: `createLeafBySplit`, `createLeafInParent`, `getLeaf('window')`, `revealLeaf`, `detach`, `setStacked`, and the reconcile plan that only writes the store.

## Conclusion

The plugin already contains the recorder that layout changes need, and the instruments that make that recorder describe a workspace the user did not build. Reconcile writes the store and leaves the split tree alone. Open, Focus, Hide, and the center overlay run first, and they change either `display` or the tree of panes, so the next pass can only claim, duplicate, or refile whatever those instruments left behind. Putting the host’s verbs on the row menus returns direction, `mod-stacked`, and percentage `flexGrow` to the code path that already knows the 200px drag floor and that already restores a vertical root on load.

What still decides whether groups stay fluid is what a group is allowed to be. A live group that is the tab group’s own children survives Obsidian’s drag, the stack toggle, and reload, because those gestures already edit that object. A dormant list stays a list until a labeled verb creates a tab group or fills one. Sections stay a way to file those lists. The stylesheet comment that withdrew a blanket `display: flex`, and the peer issues that keep putting toggles and drag regions back, are one result observed from two codebases: the direction class and the zero main-axis size are a single mechanism, and a plugin shares the layout by leaving that mechanism on Obsidian’s side of the API.
